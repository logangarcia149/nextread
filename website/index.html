Project Overview

NextRead is an end-to-end analytics portfolio project demonstrating how raw data can be transformed into a usable, validated decision-support product.

Using a dataset of book ratings, reader behavior, and genre information, I built a PostgreSQL analytics environment, cleaned and modeled the data with SQL, used Python to identify reader segments, developed a recommendation methodology, validated the results against a simpler baseline, and published the final output through an interactive Tableau dashboard and public website.

The project demonstrates the full analytical workflow: defining a problem, creating reliable data structures, applying analytical methods, validating results, optimizing performance, documenting decisions, and translating technical analysis into accessible information.

Business Problem

Recommendation systems often rely heavily on a user's existing preferences. While this can produce familiar recommendations, it may repeatedly suggest books similar to what a reader already knows.

Can readers be grouped by broader rating behavior and preferences, then use the behavior of similar readers to identify books they may rate highly—even when those books fall outside their usual choices?

The analysis needed to account for differences in how readers use rating scales, variation in genre preferences, the amount of evidence supporting each recommendation, and whether the recommendation method performed better than a simpler global approach.

NextRead addresses these challenges using normalized reader behavior, genre preferences, reader segmentation, segment-level book performance, evidence thresholds, and held-out validation.

The final product allows users to select the reader profile that most closely resembles their preferences and explore ranked recommendations through an interactive Tableau dashboard.

Public-Sector Relevance

Although NextRead uses book-rating data, the analytical workflow is transferable to government and program environments: integrating multiple data sources, validating data quality, defining meaningful population segments, developing performance measures, testing analytical assumptions, documenting methodology, and presenting results through an accessible public-facing dashboard.

Data Architecture

NextRead uses a layered PostgreSQL architecture to separate source data, cleaning, analytical transformations, and business-ready outputs. This makes the workflow easier to validate, troubleshoot, and extend while keeping reporting logic separate from raw-data preparation.

Raw → Staging → Intermediate → Mart

Database Layers

Raw: Preserves imported source data as closely as possible, providing a traceable ingestion layer for investigating source-quality issues.

Staging: Cleans and standardizes the source data, including validation, invalid-value handling, duplicate review, and preparation of reliable analytical fields.

Intermediate: Contains reusable analytical transformations such as reader behavior, genre preferences, normalized ratings, clustering features, segment-level book performance, and recommendation candidates.

Mart: Contains finalized outputs designed for reporting and decision use, including reader segments, ranked recommendations, validation summaries, and Tableau-facing views.

Why This Design Matters

The layered architecture separates data preparation from analytical logic and presentation. This supports traceability, quality assurance, repeatable reporting, and easier maintenance—principles that transfer directly to public-sector analytical and reporting environments.

SQL & Data Transformation

SQL was the primary transformation layer for NextRead. PostgreSQL was used to clean source data, create reusable analytical features, measure reader and segment behavior, generate recommendation candidates, rank books, and prepare reporting-ready views for Tableau.

The workflow emphasized traceability and reusable transformations rather than placing complex analytical logic directly in the dashboard.

Data Cleaning & Quality Assurance

  • Validated relationships between books, ratings, tags, and readers
  • Identified duplicate book-tag relationships
  • Excluded invalid negative tag counts
  • Checked row counts and key uniqueness after transformations
  • Reconciled aggregate rating totals with source data
  • Preserved source-quality issues for traceability

Reader-Normalized Ratings

Readers use rating scales differently. To account for this, ratings were evaluated relative to each reader's normal rating behavior rather than relying only on raw star ratings. 

rating - reader_average_rating AS rating_deviation

This allowed the analysis to identify books that performed above a reader's typical rating level.

Segment-Level Book Performance

After readers were assigned to segments, SQL aggregated book performance within each group using measures such as rating count, average rating, high-rating share, normalized rating deviation, and segment-specific affinity lift.

Advanced SQL Techniques

  • Common Table Expressions (CTEs)
  • Window functions
  • PERCENT_RANK() and ROW_NUMBER()
  • Conditional and filtered aggregation
  • Percentile calculations
  • CORR()
  • NOT EXISTS
  • Multi-stage joins and aggregations

Recommendation signals were normalized within each reader segment using percentile ranks: 

PERCENT_RANK() OVER (
        PARTITION BY cluster_id
        ORDER BY segment_high_rating_share
    ) AS high_rating_percentile

Performance Optimization

An early version of the recommendation pipeline generated approximately 79.9 million reader-book candidate rows. Stronger evidence and quality thresholds were moved earlier in the pipeline, reducing the optimized candidate table to approximately 12.9 million rows while maintaining recommendation coverage for every reader.

Tableau Reporting Layer

The final Tableau dashboard does not reproduce the recommendation logic. PostgreSQL instead exposes a simplified reporting view, mart.dashboard_recommendations, containing only the fields needed by the public-facing dashboard.

This keeps the presentation layer lightweight while preserving the full analytical logic and validation process in the database.

Python & Reader Segmentation

Python was used to prepare clustering features, evaluate multiple segmentation options, and identify reader groups with distinct rating and genre-preference patterns.

The objective was not simply to produce mathematically distinct clusters. The resulting segments also needed to be understandable enough to support recommendation logic and meaningful enough to explain to real users.

Feature Preparation

Reader-level analytical features were created in PostgreSQL, exported, and prepared in Python using pandas and scikit-learn.

  • Rating count
  • Average rating
  • Rating variability
  • High-rating share
  • Preference spread
  • Genre-preference features across 18 genres

Missing genre-preference values were treated as zero, representing no observed preference signal for that genre. Features were then standardized with StandardScaler so variables measured on different scales contributed more evenly to clustering.

Clustering Dataset

53,424 readers represented by 23 analytical features.

Evaluating the Number of Clusters

K-Means models were evaluated across multiple values of k rather than selecting a cluster count arbitrarily.

The evaluation considered silhouette score, inertia, cluster-size balance, interpretability, and whether additional clusters produced distinctions that were useful for downstream recommendation decisions.

Although lower values of k produced slightly stronger silhouette scores, those solutions created broader groups that were less useful for explaining differences in reader behavior. A five-cluster solution provided a stronger balance between statistical defensibility and practical interpretability.

Real-World Review

Statistical clustering does not automatically guarantee that the resulting groups will make sense to people who actually read, recommend, or discuss books.

To check the practical relevance of the profiles, I discussed the segment characteristics with active readers and people who work in libraries. These conversations focused on whether the identified preference patterns appeared recognizable and whether the segment descriptions felt plausible as real reading profiles.

This qualitative review was used as a reasonableness check rather than as a replacement for statistical validation. The feedback supported retaining the five-profile structure and helped inform the clearer user-facing names and descriptions used in the Tableau dashboard.

Why This Matters

The segmentation process combined quantitative evidence from reader behavior with qualitative review from people familiar with reading habits and book recommendations. This helped ensure that the final profiles were both analytically defensible and understandable to a public audience.

Recommendation Methodology

After reader segments were established, NextRead measured how books performed within each segment and compared that performance with how the same books performed across all readers.

The objective was to identify books that were not only highly rated, but that showed evidence of being especially well suited to a particular reader group.

Segment-Level Book Performance

For each reader-segment and book combination, PostgreSQL calculated:

  • Segment rating count
  • Average segment rating
  • Share of ratings that were 4 or 5 stars
  • Average reader-normalized rating deviation
  • Overall book performance across all readers
  • Segment-specific performance lift

This allowed the model to distinguish between books that were broadly popular and books that performed unusually well among a specific type of reader.

Controlling for Reader Generosity

Raw ratings were not sufficient because some reader groups were naturally more generous than others. Ratings were therefore evaluated relative to each reader's own average rating behavior. 

rating_deviation =
    rating - reader_average_rating

A positive deviation indicates that a reader rated a book higher than they typically rate books overall.

Segment-Specific Affinity

NextRead compared normalized book performance within each segment with normalized performance across all readers. 

segment_specific_affinity =
    segment_normalized_performance
    - overall_normalized_performance

This helped identify books that performed unusually well for a specific reader group instead of simply rewarding books with universally high ratings.

Evidence Thresholds

Books were required to meet minimum evidence and quality requirements before entering the final ranking process.

  • At least 75 ratings from the segment
  • Positive normalized segment performance
  • Positive segment-specific affinity
  • Segment-relative quality thresholds

Segment-relative thresholds were used because more generous and more selective reader groups have different rating distributions.

Final Recommendation Score

The final ranking used two primary signals:

  1. High-Rating Percentile: how strongly the book performed in 4–5 star ratings within the segment.
  2. Affinity Percentile: how unusually well the book performed for that segment compared with readers overall. 
PERCENT_RANK() OVER (
        PARTITION BY cluster_id
        ORDER BY segment_high_rating_share
    )
PERCENT_RANK() OVER (
        PARTITION BY cluster_id
        ORDER BY normalized_affinity_lift
    )

The initial ranking model applied equal weight to the two signals:

Recommendation Score

50% High-Rating Percentile + 50% Segment Affinity Percentile

The 50/50 weighting was treated as a practical modeling assumption rather than a proven optimal weighting and was later evaluated through held-out validation.

Separating Evidence from Popularity

Rating count was used as an evidence requirement rather than as a ranking bonus. This prevents highly popular books from automatically outranking less popular books simply because they have more ratings.

Popularity determines whether enough evidence exists; performance determines how strongly a book ranks.

Recommendation Output

Final ranked recommendations are stored in mart.segment_recommendations and exposed to Tableau through mart.dashboard_recommendations.

The public dashboard allows users to select the reader profile that best matches them and view the top 10, 25, 50, or 100 recommendations.

Model Validation

NextRead was evaluated using a deterministic 80/20 train-test split of the ratings data.

The training portion was used to rebuild the downstream recommendation pipeline, including segment-level book performance, candidate selection, recommendation scoring, and ranked segment recommendations. The test portion was held out and used only for evaluation.

Held-Out Evaluation

A recommendation was counted as a hit when a reader had at least one held-out book rated 4 or 5 stars appear within the model's Top N recommendations for that reader's segment.

53,341 Readers Evaluated

Performance was measured at Top 10, 25, 50, and 100 recommendation cutoffs.

Top N NextRead Hit Rate Global Baseline Relative Performance
10 4.96% 1.31% 3.79×
25 12.59% 2.39% 5.27×
50 21.80% 5.48% 3.98×
100 39.57% 10.03% 3.94×

Baseline Comparison

The baseline ranked books globally using training-data performance rather than reader segments. This tested whether segmentation added predictive value beyond simply recommending books that performed well overall.

NextRead outperformed the global baseline at every cutoff, providing evidence that segment-specific behavior contributes useful recommendation signal.

Validation Limitation

The validation was intentionally designed as a practical downstream test rather than a full rebuild of the entire clustering pipeline.

Reader segment assignments were held fixed during validation and had originally been created using the full dataset. This introduces some residual information leakage at the segmentation stage.

The results therefore support the usefulness of the segment-based ranking method, but should not be interpreted as a fully independent end-to-end validation of the complete clustering and recommendation pipeline.

Analytical Practice

Validation results are presented together with their limitations so that performance claims remain transparent and appropriately scoped.

Performance Optimization

As the recommendation pipeline developed, one of the largest performance challenges came from expanding segment-level recommendation candidates to individual readers.

An early version of the pipeline generated approximately 79.9 million reader-book candidate rows. The logic was analytically valid, but the candidate pool was much broader than necessary for downstream ranking.

Identifying the Bottleneck

The original process applied permissive evidence requirements before expanding books to individual readers. This removed clearly weak books but still allowed thousands of candidates per segment into the reader-level transformation.

Rather than optimizing the large reader-level table after it had already been created, stronger filtering was moved upstream to the segment-book level.

Profiling Before Choosing Thresholds

Candidate distributions were profiled separately for each reader segment using measures including rating count, high-rating share, normalized rating deviation, and segment-specific affinity.

Because the five reader groups showed different rating distributions, segment-relative thresholds were used instead of one universal quality cutoff.

  • At least 75 ratings from the segment
  • High-rating share at or above the segment candidate median
  • Normalized rating deviation at or above the segment candidate median
  • Affinity lift at or above the segment candidate median

Reducing the Candidate Pool

The stronger eligibility rules produced 1,254 strong segment-book candidates before reader-level expansion.

Candidates were then joined only to readers in the relevant segment, while books already rated by each reader were excluded with NOT EXISTS.

83.8% Reduction in Candidate Rows

Earlier design: 79,876,587 rows

Optimized design: 12,912,585 rows

Preserving Reader Coverage

Performance improvements were evaluated together with recommendation coverage to ensure that reducing the candidate table did not undermine the analytical objective.

  • Minimum candidates per reader: 104
  • Average candidates per reader: 241.7
  • Maximum candidates per reader: 356
  • Readers without candidates: 0

The optimized pipeline therefore reduced downstream processing substantially while preserving recommendation coverage for every reader.

Optimization Principle

Reduce unnecessary data before expensive downstream expansion rather than processing a very large dataset and filtering it afterward.

Moving stronger filtering upstream reduced the amount of data processed by later joins, scoring calculations, and reporting transformations.

Efficient data pipelines improve maintainability and resource use while preserving the information required for decision-making.

Key Findings & Project Outcomes

NextRead demonstrates a complete analytics workflow from raw data ingestion through public-facing delivery. The project combines SQL, Python, statistical analysis, validation, optimization, Tableau, Git/GitHub, and web publishing into one end-to-end portfolio product.

Key Findings

  • Reader behavior differed meaningfully across five segments, both in genre preference and in how generously or selectively readers used rating scales.
  • Reader-normalized ratings improved the recommendation logic by accounting for differences in individual rating behavior.
  • Segment-specific affinity helped distinguish books that performed unusually well for a reader group from books that were simply popular overall.
  • NextRead outperformed the global recommendation baseline at every tested cutoff.
  • At Top 25, NextRead achieved a 12.59% hit rate compared with 2.39% for the baseline, approximately 5.27× the baseline performance.
  • Upstream filtering reduced reader-book candidate rows from approximately 79.9 million to 12.9 million, an 83.8% reduction, while preserving recommendation coverage for every reader.
  • Discussions with active readers and people working in libraries supported the practical plausibility of the reader profiles produced through clustering.
